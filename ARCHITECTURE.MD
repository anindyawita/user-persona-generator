# ARCHITECTURE.md

## Research Context

Thesis: **Development of an Automated User Persona Generation System Based on Domain-Aware Large Language Model**
Author: Anindya Wita Wisesa (Anin) — Information Systems, Universitas Airlangga
Supervisors: Dr. Indra Kharisma Raharjana, Prof. Madya Ts. Dr. Shukor Sanim Mohd Fauzi

This system automatically generates *user personas* from multi-source user data (app reviews, online news, X/Twitter), using two experimental paths that are **compared** (not merged):

1. **LLM Pipeline** — filtered raw data is fed directly to the LLM, no retrieval.
2. **LLM RAG Pipeline** — data is processed through a vector database + retrieval before reaching the LLM.

Research goal: determine whether RAG improves persona representativeness and reduces hallucination compared to LLM-only generation.

## 2. Modules

### 2.1 Data Collection
- **Input**: project title + description (free text)
- **Output**: search queries per source (App Reviews, News, Twitter/X), generated by an LLM (model: Qwen3-14B)
- Queries use keyword + Boolean AND/OR combinations — see prompt template in thesis draft (§3.3 LLM Query Generation)
- Scraping: `google-play-scraper`, `app-store-scraper`, BeautifulSoup (news), Twitter API

### 2.2 Data Preprocessing
- Noise removal (HTML tags, URLs, special characters, emoji)
- Case folding, tokenization (spaCy), lemmatization, stopword filtering
- Language: English only (per scope limitation)

### 2.3 Data Quality Filtering (role-blind — IMPORTANT)
Three layers, cheapest to most expensive:
1. **Noise removal** (rule-based): minimum length, duplicates, language
2. **Domain relevance** (semantic similarity): cosine similarity between the project description embedding and each data item's embedding (`sentence-transformers`, `all-MiniLM-L6-v2` or `all-mpnet-base-v2`)
3. **Context validation** (LLM-as-judge, binary): YES/NO prompt, **must never mention role/user type** — it only judges domain relevance

> ⚠️ **Hard rule**: filtering at any layer must NOT determine or reference user role/subrole. If a prompt or piece of code starts asking "what type of user is this," that has become labeling, not filtering — and it undermines the study's validity (see §5).

Thresholds at each layer are **not final** — they're adjusted per source type (short/informal tweets vs. long/formal news). Document every threshold change in the experiment log.

### 2.4 LLM Pipeline (Path 1 — baseline, no retrieval)
- Filtered data goes directly to the LLM
- **Role Search**: LLM identifies candidate roles from the full dataset
- **Subrole Search**: LLM identifies variations within each role
- **Persona Generation**: LLM fills in persona attributes (see §4) using the same data (no additional retrieval)

### 2.5 LLM RAG Pipeline (Path 2 — with retrieval)
- **Document Processing**: chunk the filtered data
- **Vector Database Construction**: embed each chunk, index into a vector DB
- **Role Search**: general retrieval query ("who are the users of this system") → LLM identifies roles from retrieved results
- **Subrole Search**: per-role retrieval → LLM identifies variations
- **Persona Generation**: subrole-specific retrieval query (e.g., "small farmer complaints about selling price") → LLM fills attributes using evidence from retrieved data

> RAG is applied across **all stages** (profiling + generation), not just one point — this is an explicit design decision (see supervisor feedback in research notes).

### 2.6 Evaluation
- **Performance Evaluation** (quantitative): cosine similarity, BLEU, ROUGE — comparing each path's output against ground truth (still under discussion: expert-annotated vs. project description — see §4 known issues)
- **Domain Expert Evaluation** (qualitative): 1–5 Likert scale across 3 metrics — Representativeness, Usefulness, Consistency (see Table 3.3 in the draft)

## 3. Persona Attribute Schema

Based on the internal/external layer taxonomy (Karolita et al., 2024):

| Attribute | Primary Source |
|---|---|
| Name | Generated (fictional) |
| Age | News |
| Job | News |
| Personal Story | News |
| Core Value | Twitter/X |
| Personality Traits | Twitter/X |
| Goals | App Reviews + News |
| Pain Points | App Reviews (negative sentiment) |
| Technology & Interaction | App Reviews |
| Evidence | Quote/summary traceable to source data |
| Confidence Score | 0–1, based on evidence strength (not general model knowledge) |

Every attribute **must** be traceable to source evidence. If evidence is insufficient, use `null` / `"Not specified in the available data"` — never fill from the LLM's general knowledge (hallucination risk, see Chapter II).

## 4. Known Design Tensions (read before touching filtering/role-search logic)

1. **Filtering vs. Labeling**: filtering MUST be role-blind. If you're adding "data classification," make sure it classifies *quality/domain relevance*, not *user type* — otherwise the research becomes circular (you determine the role, not the LLM).
2. **Evaluation ground truth**: the Chapter III draft still contradicts itself between "ground truth = project description" vs. "ground truth = expert-annotated." This MUST be resolved before implementing evaluation — pick one; it affects the construct validity of the research claim.
3. **Thresholds are not fixed**: don't hardcode a single global value. Make thresholds configurable per data source (app review, news, tweet differ in length/style).
4. **Don't cut off LLM reasoning**: don't pre-assign role/subrole outside the LLM (see §2.3). If you need to reduce an excessive number of subroles, do it at the **post-generation validation** stage (filter by confidence score/evidence), not by restricting the input.
