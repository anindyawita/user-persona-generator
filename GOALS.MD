# GOALS.md — Research Goals & Ground Truth for This Thesis

This file is the **source of truth about what this research is trying to prove.** It doesn't describe how the code is organized — that's `ARCHITECTURE.md` — or how to work in this repo — that's `CLAUDE.md`. When those two files disagree with each other, or a new decision needs to be made, check it against this file first: whichever option keeps the research question answerable and the design defensible in a thesis defense is the one that wins.

## 1. Research Problem

> How can a Large Language Model (LLM) generate user personas that are domain-aware, relevant, and representative, based on multi-source user behavioral data?

## 2. Research Objective

Develop an LLM-based framework that generates user personas that are domain-aware, relevant, and representative, grounded in multi-source user behavioral data — as an alternative to both fully manual persona creation (slow, subjective, small-sample) and fully generic LLM-only generation (fast, but generic and hallucination-prone).

## 3. Why This Matters (the gap this thesis fills)

- Manual persona creation is accurate but expensive, slow, and limited by how much data an analyst can realistically process.
- LLM-only persona generation (prompt-only, no external grounding) is fast but tends to produce generic personas that reflect the model's general knowledge rather than the actual target users — because there's nothing forcing it to stay grounded in real data.
- This thesis's contribution is testing whether adding domain grounding via Retrieval-Augmented Generation (RAG) measurably improves persona quality over an LLM-only baseline, using real multi-source data (app reviews, online news, Twitter/X) rather than a single data source (which is what most prior work does).

**This is the load-bearing design decision**: the two-pipeline comparison (LLM-only vs. LLM+RAG) is not an implementation convenience — it *is* the experiment. If any refactor merges the two pipelines, lets one influence the other, or removes the ability to compare them independently, it destroys the thing this thesis is trying to measure.

## 4. What the System Must Be Able to Demonstrate

For the research question to be answerable, the final system must be able to show, for the same input data:

1. What a persona looks like when generated by an LLM alone (no retrieval).
2. What a persona looks like when generated by an LLM with RAG-based domain grounding.
3. A measurable difference between the two — via both:
   - **Performance metrics** (cosine similarity, BLEU, ROUGE) comparing outputs against a ground truth.
   - **Expert evaluation** (Likert scale) on representativeness, usefulness, and consistency.

If a technical decision would make it impossible to isolate and compare these two conditions cleanly, that decision conflicts with the research goal — flag it, don't just implement it.

## 5. Non-Negotiable Constraints (derived from supervisor feedback, already settled — do not re-litigate)

These came out of direct correction from the supervisor (Dr. Indra Kharisma Raharjana) during proposal review. They are settled, not open for silent reinterpretation:

- **Two independent pipelines, always compared, never merged.** LLM Pipeline and LLM RAG Pipeline must run separately and produce separate outputs.
- **Role and subrole must be discovered by LLM reasoning, not pre-assigned.** Any data classification step (e.g., quality filtering) must be *role-blind* — it may judge domain relevance, never user type. If a classifier starts distinguishing "this is a farmer post" vs. "this is a consumer post" before the LLM does its own role search, that has quietly turned into labeling, which defeats the point of testing whether the LLM/RAG *finds* roles on its own.
- **Every persona attribute needs traceable evidence.** No attribute may be filled from the model's general knowledge without a supporting quote/reference in the source data. If evidence is insufficient, the field is left explicitly unfilled (`null` / "Not specified in the available data"), never guessed.
- **Thresholds (filtering, confidence) are not fixed constants.** They vary by data source (tweets vs. news vs. app reviews have very different length/style), and this variability is itself something the thesis needs to report honestly, not hide behind a single hardcoded number.

## 6. Persona Attribute Schema (what "a persona" means in this project)

Per the thesis's Internal/External Layer taxonomy (Karolita et al., 2024) and the actual generation prompt design:

Name, Age, Job, Personal Story, Core Value, Personality Traits, Goals, Pain Points, Technology & Interaction — plus, for every attribute: **Evidence** (the supporting quote/source) and an overall **Confidence Score** (0–1, based on evidence strength, not general model knowledge).

If ARCHITECTURE.md's schema and CLAUDE.md's schema ever disagree, this list is the tiebreaker.

## 7. Evaluation Design (what "better" means in this project)

Two complementary evaluation tracks, not one:

- **Performance evaluation**: cosine similarity, BLEU, ROUGE — comparing LLM Pipeline output vs. LLM RAG Pipeline output against a ground truth. *(Open question, not yet settled: whether ground truth = the original project description, or expert-annotated persona data. This must be resolved before evaluation code is built — see ARCHITECTURE.md §4.)*
- **Expert evaluation**: 1–5 Likert scale on representativeness, usefulness, and consistency, from domain experts (UI/UX, requirements engineering, or project management background).

## 8. Scope Boundaries (what this thesis is NOT trying to do)

- Not fine-tuning an LLM — uses pretrained/API models as-is.
- Not evaluating business performance or large-scale industry deployment — evaluation is limited to relevance, representativeness, and quality vs. manual persona creation.
- Not multilingual — English-language data only, per data source availability.
- Not solving data access for real end-users — the entire point of this framework is to let developers simulate/profile users from public digital traces (reviews, news, social media) *because* direct access to real users is often limited in practice. Don't "fix" this by proposing the system collect data from real interviewed users instead — that would eliminate the problem the thesis exists to address.
